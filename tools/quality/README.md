# 技术质量门禁

`pnpm check` 检查当前实现；`pnpm verify` 为将要提交的精确 Git tree 生成证据。只在本地运行，不使用 GitHub Actions/CI。

## 执行链

1. 静态检查拒绝空实现、忽略输入并恒定返回成功的公开入口、较大复制实现、无行为转发函数、不可达模块、空测试和 skip/only/todo 等测试旁路。
2. 使用独立临时索引捕获工作区，或直接捕获暂存区/指定提交。验证在临时目录完成，独立安装依赖与构建，避免未暂存修复和旧 dist 让待提交代码假通过。
3. 执行完整 build、类型、lint、依赖、生成物、单元及浏览器检查；解析报告，拒绝零测试、跳过、重试通过、测试身份消失及测试计数不符。
4. 旧测试或夹具变动时，从受信 Git tree 恢复旧测试与夹具，再运行于新实现。旧断言不能被同时修改来掩盖实现回归。
5. 在内存变换中注入移动失效、冷却/距离绕过、护盾不扣除、装备丢失、药水无效、重复拾取、精灵锚点错误、攻击输入断线、血条留白这 10 种故障。指定契约必须实际失败；没有注入、测试没发现、编译/收集失败都不算检测成功。
6. `e2e/acceptance` 通过键盘、UI 和浏览器时钟驱动真实游戏，只读状态。禁止调用调试命令、step、spawn、load 等接口替代玩家操作，也禁止在 evaluate 中修改状态。覆盖移动/松键、暂停恢复、战斗/拾取/换装、快捷键存读档、可见血条和完整清层续层。

## 提交与推送

```bash
pnpm verify                  # 不修改真实暂存区，验证完整工作区
pnpm verify --staged         # 验证真实暂存区；部分暂存时使用
pnpm verify --commit <sha>   # 验证指定提交
```

`pre-commit` 验证实际 index tree；`pre-push` 检查所有将推送的提交。相同 tree、策略、契约基线与 Node 版本可复用本地签名证据；任何变化都失效。

`pnpm install` 的 prepare 在首次克隆时从已提交的 HEAD 安装门禁。运行器、规则快照、契约基线、签名密钥和 hooks 存在 Git 元数据目录；修改工作区门禁脚本不会替换正在执行的 hook。再次安装保留已有信任，不自动认可工作区变更。

初次引入尚未提交的门禁，维护者在完整验证后执行 `pnpm quality:install --bootstrap`。后续策略升级须经明确审核：

```bash
pnpm verify --review-policy       # 仍由已安装运行器验证旧契约与故障集
pnpm quality:install --reviewed   # 显式采用审核过的精确 tree
pnpm verify                      # 新策略也必须通过自身完整验证
```

普通实现任务不得自行使用上述审核选项、推进信任基线、设置跳过 hook 或删除签名密钥。只有维护者明确要求审核/更新门禁时才能执行。

## 检查范围

复制检测比较函数 AST，保留全局调用、属性和字面量，仅归一化参数与局部绑定；只检查至少 5 个语句、120 个节点的实现，不把短声明和测试夹具当复制。转发函数应改成直接 export alias，真正进行校验、转换的适配层保留。不可达检查从 package exports/bin/scripts、游戏入口与测试建立模块图。

这些检查验证客观行为与回归敏感度，不判定主观趣味，也不证明任意新增算法都正确。新能力需要补其行为契约和有代表性的故障；通过标准不能用增加空断言或放宽门槛来替代。

同一账号拥有 Git 元数据和推送权限时，可刻意移除任何本地门禁；本机制防止普通代码变更悄悄弱化验证，不声称是对抗同权限恶意操作者的安全边界。
